## 1. SRS 符合 IEEE/ISO 標準的《純需求規格書（Pure SRS） 嗎?

提問時間：**2026-10-24 11:26:44 +08:00**（原始 UTC `2026-10-24T03:26:44.615Z`，紀錄第 3 行）。

**使用者提問**

> SRS 符合 IEEE/ISO 標準的《純需求規格書（Pure SRS） 嗎?

**AI 回覆**

**不符合。** 這份 SRS 是需求加設計的混合文件，不是純 SRS。它也沒有完全對齊 ISO/IEC/IEEE 29148:2018，那是取代 IEEE 830-1998 的現行標準。以下是我依這兩份標準的原則逐項對照的判斷，不是正式稽核。

#### 1. 主要問題：混入大量設計內容

純 SRS 只寫系統必須做到什麼（what），並讓每條需求可驗證，不規定怎麼實作（how）。下列內容都屬於設計：

| 位置 | 屬於設計的內容 |
| --- | --- |
| 每個 FR 的「函式規格與實作方向」 | 函式簽名、REST 路徑、HTTP 狀態碼、錯誤代碼、`WHERE id=? AND version=?`、Cookie 的 Secure／HttpOnly／SameSite、CSRF、Outbox |
| 第 6 章 | 類別圖、內部函式流程圖，例如 `lockSubmissionAndVerifyAttemptOwnership()`、`reserveFiniteInventoryConditionally()` |
| 7.3 | 模組責任劃分 |
| 7.4 | UNIQUE 限制、CHECK 限制、索引建議 |
| 7.6 | JSON 請求與回應範例 |
| 其他 | `commandId`、`expectedVersion`、`Idempotency-Key`、`attempt token`、`租約` 等機制 |

文件在多處自稱「設計提案」，也說明「不指定程式語言、框架」，意圖是對的。但第 6、7 章加上各 FR 的實作方向，已經實質規定了架構。IEEE 830 也要求把設計限制與需求分開。

SAD v0.1 又重寫了同一批內容：冪等、鎖順序、Outbox、資料表、端點。同一件事寫在兩份文件，之後很容易互相矛盾。

#### 2. 其他不符之處（對照 29148）

| 29148 的要求 | 現況 |
| --- | --- |
| 單一性：一條需求只表達一件事 | 多數 FR 把數個行為包成一條，例如 FR-014 同時涵蓋驗證、建立、保留、失敗回滾和取餐碼 |
| 完整性：不應有 TBD | 15 項 B-xx 待決議，其中 B-04（容量單位）、B-09（接單後釋回）、B-11（統計口徑）直接影響驗收。文件有誠實標示，但需求仍未完成 |
| 可驗證性：量化、可測 | 「重新驗證」「提示可理解」等措辭偏軟。CAP 和 NFR-003 只是暫定值 |
| 結構：29148 的 SRS 範本含參考文件、假設與相依、設計限制、驗證章節 | 缺獨立的參考文件章節（只在抬頭引用 PRD）、缺假設與相依性章節、缺設計限制章節。驗證只有 AC 加附錄 A |
| 需求屬性：ID、優先級、來源、狀態、驗證方法 | 只有 ID、來源（PRD）和 AC。優先級只用「全部 Must」帶過，沒有逐條的狀態與驗證方法欄位 |
| 用語：統一使用 shall | 用「須」「應」「建議」混雜，強度不一 |

#### 3. 文件內部的不一致

- 附錄 A 引用第 7.7、7.8 節，但第 7 章只到 7.6。
- FR-014 寫「交易邊界導讀見第 7.4 節」，但 7.4 是資料限制與索引建議。
- SAD 的追溯表指向「SRS v0.2」，目前這份是 v0.3。git 紀錄寫「SRS v0.3 至 v0.4」，檔名和內文仍是 v0.3，版本號需要對齊。

#### 4. 做得好的部分

- 26 條 FR 與 AC 一一對應，也能追溯到 PRD。
- 範圍排除明確：無付款、退款或財務對帳。
- 角色邊界、狀態轉換表、資源處理表都清楚。
