## 部署、維運與故障恢復

### 環境與發布

**模擬交付部署（Q5 定案，2026-11-26）**：本案依 SRS A-13 為模擬交付，正式環境為專案負責人的個人電腦，以 Docker Compose 在單一主機部署，預算為 0。

| 元件 | 選擇 | 說明 |
| --- | --- | --- |
| 前端／API／Worker | 三個容器；API 與 Worker 為同一 NestJS 程式碼庫，React 建置為靜態檔 | 技術方向依 D-01 |
| 資料庫 | 單一 PostgreSQL，WAL 持續歸檔至另一個 volume | 不設備援機；以 WAL 支援 RPO 15 分鐘 |
| 郵件 | Mailpit（本機 SMTP 收信工具） | 所有合成信箱的驗證信都在 Mailpit 介面收取，不使用真實網域 |
| 刪除復原日誌 | 獨立 PostgreSQL schema，使用專屬資料庫角色，備份分開存放 | 與業務資料權限分離 |
| HTTPS | 本機憑證（mkcert） | 對應 SRS EI-004 |
| 監控 | 健康檢查加上每分鐘一次的可用性探測腳本 | 對應 SRS NFR-005 |

專案負責人擔任維運聯絡人、技術負責人與首位管理員（SRS A-13）；文件不記錄個人姓名或信箱，首位管理員與測試帳號一律使用合成信箱，例如 `admin@campus-order.test`。

同一台電腦上只分「開發」與「正式（模擬交付）」兩組 Docker Compose 專案，各自使用獨立的 DB volume、Mailpit 與秘密，不另設預備環境；兩者都只使用合成帳號及餐點資料，驗收、壓測與還原演練直接在正式環境執行。

**D-09 發布流程**：型別與靜態檢查 → 規則測試 → 真實 DB 整合測試 → 三角色端到端測試 → migration 相容性驗證 → 正式環境發布與冒煙檢查 → 以合成資料驗收。正式環境使用版本化映像與 migration，不手動修改 schema。

資料庫變更採先擴充欄位、相容讀寫、回填核對、最後移除的方式。應用回滾只在資料結構仍相容時執行；已寫入的新資料不能用盲目反向 migration 刪除。API 與 Worker 混合版本期間，Outbox payload 須有 schema version 且消費端相容。

模擬交付只有一個 API 與一個 Worker 容器，不設 API 副本、DB 備援或自動故障切換；主機、API 或 DB 故障時核心服務停止，依 [備份與復原](#備份與復原) 恢復，因此本部署不描述為高可用。日後若轉為實際上線，再依成本與 NFR-005 實測結果評估增加副本與備援。

### 監控與告警

| 類別 | 指標與觀測 | 失效時行動 |
| --- | --- | --- |
| HTTP | 錯誤率、端到端延遲、授權拒絕、429 | 區分業務衝突與系統故障，依 requestId 追查 |
| DB | 連線池、鎖等待、死鎖、慢查詢、儲存量 | 限制過量請求，調查熱門資源與查詢計畫 |
| 業務一致性 | 負庫存、時段占用超過容量、保留加總差異、唯一鍵異常 | 告警並限制受影響的新單，不改寫已成立訂單或任意補回資源 |
| 背景工作 | 最舊 Outbox 年齡、重試數、逾時未完成的領取、PROCESSING 停滯 | 最舊待投遞通知超過 5 分鐘、最舊到期未取消訂單超過 2 分鐘、PROCESSING 超過 2 分鐘或重試超過上限即告警；恢復工作或人工處理，不重跑業務事件 |
| 使用者可見性 | 訂單提交至畫面更新延遲、輪詢失敗率 | 檢查 API、前端輪詢與網路，顯示過期資料 |
| 可用性 | 每分鐘一次可用性探測；探測失敗的分鐘計為不可用 | 告警維運聯絡人；依服務可用率計算時段計算可用率 |
| 外部依賴 | 驗證郵件寄送失敗 | 暫停受影響功能，保留既有有效資料 |
| 復原能力 | 備份成功時間、備份可讀性、最近演練結果 | 追查失敗備份與未達復原目標 |

系統運作日誌串聯 requestId、submission 識別摘要、orderId、commandId、eventId；不記錄完整個資、proof 或 Cookie。背景工作告警門檻見 [Notifications：到期處理與恢復方向](./07_通知與工作台_Notifications.md#到期處理與恢復方向)；維運聯絡人（SRS A-05）依 A-13 由專案負責人擔任。

### 備份與復原

**D-10**：資料庫每日全量備份並持續歸檔變更紀錄，支援 RPO 15 分鐘；日備份保存 30 天，採分離權限與加密保存。RTO 為 4 小時；每月可用率目標 99.0%，以服務可用率計算時段（每日 07:00–20:00，扣除全校休息日）計，計畫維護安排於該時段之外。模擬交付只驗證探測、告警與可用率計算機制可運作，「每月 99.0%」在驗收報告列為無法實證的限制；RPO 與 RTO 仍以還原演練實測。上線前至少完整還原一次，之後每六個月演練一次；數值來自 SRS v0.6 NFR-005，尚無達標實測。

復原順序：停止寫入及 Worker → 選擇一致復原時間點 → 還原 DB、設定與金鑰 → 套用核定清除清單 → 檢查訂單、庫存、容量、submission、通知及 Outbox → 核對可能遺失時段的人工交付 → 受控恢復服務。

若復原點早於現場已交付時間，可能出現資料與實體交付不一致；須依已保存的事件與商家紀錄人工確認，不得批次將訂單假設為完成或重新出餐。復原演練應記錄實際耗時與資料差距，作為 NFR-005 的驗收證據，包含已刪個資未重新出現的檢查。

### 降級策略

| 故障 | 對使用者的行為 | 一致性處理 |
| --- | --- | --- |
| DB 無法連線 | 受保護查詢及寫入回暫時不可用 | 不依快取承諾建單成功；恢復後查原 key |
| Worker 停止 | 訂單詳情與商家清單仍可查；通知與逾時取消可能延遲，須告警 | 接單入口仍禁止逾時接單並落實取消；當日庫存由讀寫入口補初始化；恢復後補掃取消、送單恢復與去重投遞 |
| 郵件服務故障 | 新驗證無法完成；既有有效 Session 仍可用 | 不繞過驗證、不建立未驗證登入 |
| 用戶端斷網 | 顯示連線中斷及最後更新時間 | 不自動換 key 或離線宣告送單成功 |

## 容量與效能驗證設計

SRS v0.6 CAP-001～005 基準為約 3000 個學生帳號、500 人在線、30 家商家、每家 100 項商品。學生 470 人、商家 30 人；學生操作比例為瀏覽 55%、購物車與確認 20%、送單 10%、查單 15%。升載 5 分鐘後維持 30 分鐘，均勻流量與單一熱門商家／時段各測一次。學生端模擬 4G（單向約 50 ms、約 10 Mbps），商家端不另加延遲；受測系統即模擬交付的正式環境，壓測方式見下方〈模擬交付的壓測方式〉。

CAP-003 指定的主要頁面與一般操作 p95 不超過 3 秒、錯誤率低於 1%；管理後台查詢與統計不列入 3 秒門檻但不得逾時失敗。正常前景狀態更新 95% 在 10 秒內。負載工具、思考時間及系統故障／預期業務拒絕的統計分類由測試文件列明並分別報告，不以平均值或每秒 500 筆送單替代要求。

以 D-06 的 5 秒輪詢為估算，若 500 位前景使用者各有一個合併輪詢，平均約為 `500 / 5 = 100 次讀取／秒`，尚未包含瀏覽、建單、狀態操作及同使用者多頁籤。此為容量估算，不是效能實測結果。

**模擬交付的壓測方式**：負載產生器（例如 k6）與受測系統在同一台電腦執行，驗收報告須註明「負載產生器與受測系統同機，結果偏保守」；學生端 4G 延遲由負載工具對每次請求加約 50 ms 模擬，不另架網路模擬器。未達門檻時先記錄實測數字，不調低門檻，再評估改用第二台電腦產生負載。

**D-11 優化順序**：先建立查詢索引與分頁、限制欄位及日期範圍、縮短交易、調整連線池，再量測是否需額外快取或推送。靜態網站可快取；庫存與容量快取只作提示，送單仍讀權威 DB。私人訂單回應不可進入公開共用快取。

管理查詢負載另測，不改主情境組成。除延遲分布外，同時核對訂單唯一性、庫存、容量、狀態事件及通知一致性。正式通過門檻依 [SRS v0.6](../SRS.md) 的 §3.4（CAP-001～005、NFR-003）與 §3.7 NFR-005。

## 驗證策略與關鍵情境

本節為待執行測試設計；詳細步驟與測試資料由獨立測試文件依 SRS v0.6 有效的 AC-001～007、AC-009～028 展開（AC-008 已廢止），尚無實測結果。

| 測試類別 | 重點情境 | 必須證明的結果 |
| --- | --- | --- |
| 規則測試 | 商品上下架、數量、精確計價、時段邊界、六狀態轉換 | 非法輸入與非法轉換拒絕，金額可重算 |
| 菜單可見性 | 下架、重新上架、商家管理查詢、舊菜單與舊購物車 | 下架商品不出現在點餐者菜單及回應；商家仍可管理，重新上架後可見；舊資料不可繞過下架檢查，既有訂單快照可查 |
| 真實 DB 整合 | 建單第二項保留／快照失敗；訂單狀態操作必要操作紀錄失敗 | 整單回滾，無殘留資源或成功結果 |
| 並行資源競爭 | 最後一份庫存／最後一單位容量、手動調整同時送單 | 最多符合資源數量的訂單成功，無負值 |
| 去重與恢復 | 同 key 並行 10 次、回應遺失、claim 後當機、領取時限到期 | 只一張訂單及一次資源占用，可查回結果 |
| 狀態競爭 | 接單對取消、完成對未取、同 commandId 重播 | 一個合法結果；相同狀態操作不重複事件 |
| 商品與庫存邊界 | 上架但庫存為 0、下架但庫存足夠、下架後釋回／每日重置、僅商品資料版本變更 | 所有商品均檢查並保留庫存；商品狀態與庫存互不改寫；資格重驗；內容相同不因版本不同要求重確認 |
| 價格及快照 | 報價後改商品或價格、總價剛好相同但明細不同、成立後改名改價 | 送單前重新確認，成立後快照不變 |
| 取餐 | 錯碼、未確認交付、非商家、時段結束前／當下／之後 | 只有合法交付完成；未取需嚴格超過結束時間 |
| 通知 | Worker 寫入後當機、重複事件、權限撤銷後讀舊通知 | 一收件者一事件最多一筆通知，無越權內容 |
| 授權 | 換學生／商家 ID、停用後持舊 Session、角色變更 | 受保護請求拒絕，重播也不繞過授權 |
| 端到端與介面 | 三角色主流程、載入／空／失敗／斷線、手機必要按鈕 | 使用者可理解結果並沿原操作恢復 |
| 負載與復原 | 核定 500 人情境、熱門時段、備份還原 | 效能與一致性同時符合核定目標 |
| 新基線競爭 | 同學生跨商家並行送單、商家停用與接單、逾時取消重試、昨日釋回 | 三張上限、系統取消一次、當日庫存不被昨日釋回增加 |
| 個資刪除與復原 | 刪除與送單競爭、通知重投、刪除途中當機、還原舊備份 | 無進行中才刪、不可重建已刪資料、統計重算、歷史資源不誤補回 |
| 新政策邊界 | 固定提前 10 分鐘截止、容量調低與送單競爭、已使用時段刪除、無效期價格確認、操作結果二十四小時、五次錯碼 | 截止前一刻可預訂、當下起拒絕；容量不得低於占用，違規修改不生效；曾使用時段取消或個資刪除後仍不可刪，從未使用且無引用者可刪；內容相同仍有效、舊操作不重跑、鎖定可跨程序生效 |
| 範圍回歸 | API、schema、畫面及報表掃描 | 無付款、退款、收款狀態與財務對帳功能；無客製化選項介面、欄位與加價計算；無商品圖片、分類、獨立售完開關或獨立價格版本；無庫存模式選擇或略過庫存保留的分支 |

驗收紀錄須包含環境、資料集、版本、操作步驟、預期與實際結果、缺陷及核准人；架構設計完成不等於功能驗收通過。

## 實作順序與交付條件

| 階段 | 主要產出 | 完成條件 |
| --- | --- | --- |
| 1. 基線確認 | SRS v0.6 追溯、缺少來源補齊、設計審查紀錄 | 核心狀態、容量、資源釋回、權限及欄位有可測試定義 |
| 2. 技術骨架 | Module 結構、DB migration、Session、授權、觀測 | 三角色可驗證，停用及越權測試通過 |
| 3. 訂單核心 | 菜單、購物車、報價、保留、送單去重及快照 | 真實 DB 並行、回滾及未知結果恢復通過 |
| 4. 營運流程 | 訂單狀態操作、自動取消、取餐、未取、通知、後台、統計與個資刪除 | 三角色端到端與事件／資源核對通過 |
| 5. 上線驗證 | 負載、裝置、備份復原、告警及操作手冊 | 全部 Must 與核定 NFR 有實際測試證據及驗收核准 |

## 採用方向衍生的驗證

採用與定案經過見 [SAD 入口](../SAD.md#本版採用內容)。依採用方向新增的驗證包含各角色 Session 到期、持續輪詢不能續期、刪除各階段當機、多頁籤使用不同報價、已刪除未使用時段的舊購物車，以及已使用時段的刪除拒絕及商家停用預覽版本競爭。
