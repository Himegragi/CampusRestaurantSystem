## 系統範圍與架構

提供學生點餐、商家接單備餐與管理員管理查詢。單一校園、繁體中文、Asia/Taipei；付款由現場處理，系統不包含金流、退款、收款狀態或財務對帳。2026-11-05 依使用者決議移除客製化選項功能，FR-008／AC-008 已廢止。

先採 React + TypeScript 前端、NestJS 模組化單體後端、單一 PostgreSQL，另以共用程式碼的 Worker 執行通知、逾時取消與恢復工作。瀏覽器透過 HTTPS 呼叫 API；後端負責授權、價格、資源及狀態判斷。郵件僅供登入驗證。商品模組已於 2026-11-05 移除圖片與分類，狀態只有上架／下架；所有商品統一為有限庫存，可用量與每日預設量由 Resources 管理，不另設售完開關。

完整關係見 [圖 0：全系統 UML 架構總覽](./SAD_v0.6/00_系統架構與模組分工.md#圖-0-全系統-uml-架構總覽)。

## 九個業務模組

| 模組 | 主要責任 |
| --- | --- |
| Identity | 電子郵件驗證、Session、權限、帳號狀態與學生個資刪除 |
| Merchant | 商家、營業區段、接單開關與停用流程 |
| Catalog | 商品名稱、商品單價、商品上下架與商品資料版本 |
| CartQuote | 單店購物車、後端計價與確認內容 |
| Resources | 按營業日庫存、取餐時段、容量與資源保留／釋回 |
| Orders | 建單、歷史快照、狀態命令、去重與交易協調 |
| Notifications | 站內通知、商家新單提示與提交後投遞 |
| AdministrationQuery | 訂單查詢及依現有訂單計算的營運統計 |
| Audit | 重要異動與必要失敗紀錄、管理員查閱 |

Outbox、資料存取、郵件、備份與監控是共用基礎設施。九個模組屬同一應用，不需要各自部署成獨立服務。

## 四條主要流程

| 流程 | 核心做法 |
| --- | --- |
| 登入 | 寄六位一次性碼；驗證成功才建立登入。每次受保護請求重新檢查帳號、角色及資料範圍 |
| 送單 | 購物車與報價不占資源；提交後重驗內容、三張上限、供應與截止，訂單、庫存、容量、快照及成功結果同交易提交；失敗整單回滾 |
| 訂單操作 | 待確認 → 製作中 → 可取餐 → 已完成；合法取消轉已取消。未取由商家在時段結束後、已備妥且未交付時標記；終止狀態不再轉換 |
| 通知與刪除 | 需通知的事件同交易寫入 Outbox，提交後去重投遞。學生無進行中訂單才可刪帳號及全部訂單；還原備份前須重套刪除，不能讓資料復活 |

訂單生命週期見 [圖 6：訂單狀態圖](./SAD_v0.6/06_訂單與交易_Orders.md#圖-6-訂單狀態圖)。

## 不可違反的規則

- 同一次送單或狀態命令重送，回原結果；未知結果沿原識別查詢，不能換識別重建。詳細結果保存 24 小時，過期識別不重新執行。
- 庫存及容量在建單時保留。接單前取消退原營業日庫存及容量；接單後取消只退容量；完成與未取都不退資源。
- 容量按餐點份數計算。調低至小於既有占用時保留舊單、拒絕新增超額占用；剩餘量顯示不小於 0。
- 商家停用取消全部進行中訂單；待確認到取餐時段結束即符合系統取消條件。製作中及可取餐不因時段結束而自動取消，系統不自動標記未取。
- 營業日結束後不能再核碼完成或把製作中改成備妥；商家僅能取消，或對已備妥未交付者標記未取。
- 取餐碼只供本人學生查看；商家選定訂單後輸入核對，管理員也不可讀碼。歷史名稱與價格採成立快照。
- 個資刪除後統計依現存訂單重算；歷史資源占用不因刪除被誤加回。操作紀錄保留，但解除學生及已刪訂單的可識別關聯。

## 最需要團隊確認的部分

依 2026-11-02 指示先採以下建議方向；Q6 效期已採用為本版設計值；部署資源及背景工作時間仍需定版。

| 優先 | 要確認什麼 | 建議方向 |
| --- | --- | --- |
| P0／Q1 | 刪除途中當機或日誌失敗怎麼恢復？ | 持久刪除請求、封鎖存取、獨立日誌與可重試清除；完成後才回成功 |
| P0／Q2 | 誰負責整店停用的共同交易？ | 由應用層協調入口管理，避免 Merchant 與 Orders 直接互相依賴；預覽變動須重新確認 |
| P0／Q3 | 學生確認報價的紀錄怎麼保存？ | 採建單時確認；不可讓新報價或清理作業破壞仍有效的確認與恢復 |
| P1／Q4 | 已使用時段能否實體刪除？ | 封存設定並保留歷史參照，未引用者才實體刪除 |
| P1／Q5 | 採哪套環境、誰維運？ | 核定技術、部署與備援、郵件、預算及負責人 |
| P1／Q6 | 登入多久到期、共用帳號怎麼用？ | 學生 24 小時／閒置 30 分鐘；商家 12 小時／60 分鐘；管理員 8 小時／15 分鐘 |
| P1／Q7 | 取消與恢復多久內必須完成？ | 定義排程、租約、重試及告警參數，驗證逾時邊界；不得自行放寬 SRS |

詳細原因、選項及來源見 [審查與待確認清單](./校園點餐系統_SAD_v0.6_審查與待確認.md#最需要先確認的事項)。SRS 已決定的業務規則不需重選；本次採用方向已記錄；部署資源、尚缺參數與實測結果仍須補齊。

## 實際使用情境

- 刪除按下後當機：先封鎖舊資料，恢復後沿同一請求完成清除，不誤刪同信箱的新帳號。
- 停用預覽有 5 張單，確認前變成 6 張：顯示最新數量，重新確認後才整店取消。
- 兩個分頁各有報價：新報價不覆蓋舊報價；送單帶指定 quoteId，內容未變就仍可驗證。
- 刪除有已完成訂單的時段：設定畫面移除，歷史資料保留；禁止新預訂。
- 午餐尖峰主機故障：須有備份權限與負責人實際執行復原，不能只在文件寫 RTO。
- 管理員 09:10 離席：即使畫面持續輪詢，09:25 仍閒置登出；商家則給 60 分鐘備餐緩衝。
- 12:30 應取消的訂單遇 Worker 停機：需要補掃及入口校正，避免過期單一直占學生三張上限。

Session 兩種期限任一先到即失效，背景輪詢不續期。到期前 2 分鐘提醒，重新登入不會取消訂單；未知送單結果仍查原識別。各角色完整時間與情境見 [Q6](./校園點餐系統_SAD_v0.6_審查與待確認.md#q6)。
